# compress-lib v1.1.0

**Fixes from an external review of 1.0, and faster, smaller compression at levels 4 to 9.** The review found no critical or high issue: about three million fuzzed and crafted streams decoded with zlib's verdict and bytes. It found one medium and four low issues, fixed here with a regression test for each. The 1.x API is unchanged; 1.1 only adds to it.

## Fixed

- **The ratio cap now covers a whole gzip stream (medium).** `Limits::max_ratio` and its 1 MiB floor used to start again at every gzip member, so a bomb split into small members was never ratio-checked: 60 members of a megabyte of zeros (60 KB on the wire, 60 MB out) passed `with_max_ratio(50)`. The absolute output cap still held. Now every member counts towards one ratio.
- **`io::DecodeReader` refuses bytes after a raw or zlib stream**, as the one-shot functions, `DecodeWriter`, and gzip already did. It used to stop at the end and drop what followed, which is the smuggling case T-13 closes. `with_trailing_data(true)` is the new way to stop at the end on purpose.
- **`DictionaryRequired` is resumable.** A `zlib::Decoder` that meets a stream naming a preset dictionary now waits for it: read `dictionary_id()`, call `set_dictionary`, and continue with the input from the error's `offset()`. `set_dictionary` used to return `Ok` without effect.
- **A `Deflater` stays at the memory it was built with.** Blocks could pile up in its output buffer, each with room for 6 bytes per symbol, so a level-6 deflater built at 396,280 bytes could grow to 527,416. Each block now reserves its exact size, and the engine waits for a drain before the buffer could outgrow its first allocation.
- **`gzip::Decoder::reset` works for reuse.** A reset decoder kept the last member's length and refused its next stream with `LengthMismatch` (found while testing the fixes).
- Documentation: memory figures for `message::Compressor` and `Inflater::decompress_vec`, and the rule that gzip trailing data must not begin with the gzip magic.

## Changed

- **Levels 4 to 9 hash four bytes and search within a budget.** A three-byte hash made long chains on binary data, and crafted input could make every position search 4,096 candidates at level 9 (under 1 MB/s). Levels 4 to 9 now hash four bytes, and a lazy search that wants more than 16 chain steps spends from a budget of 64 per input byte, banked up to one window's worth: more than ordinary data uses. Timed against 1.0.0 in the same jobs on hosted Linux, macOS, and Windows runners, level 6 is 1.1 to 1.9 times as fast on text and binary input and level 9 1.7 to 2.5 times, with output up to 2.9 percent smaller on every benchmark corpus; on crafted input level 9 is 3.6 to 30 times as fast. JSON and HTML gain less, and level 1 is unchanged within what the benchmark can resolve, except macOS level 1, which reads 0.90 to 0.96 of 1.0 (see `docs/PERFORMANCE.md`). Levels 0 to 3 produce the same bytes as 1.0.
- `Debug` for the zlib and gzip types shows a preset dictionary by length only, and never header fields or output in waiting.

## Added

- `io::DecodeReader::with_trailing_data(bool)`.
- `wipe()` on `zlib::Decoder`, `zlib::Encoder`, `gzip::Decoder`, `gzip::Encoder`, `Decoder`, and `Encoder`.

## Verified

- FUZZ_PLACEHOLDER
- SOAK_PLACEHOLDER
- cargo-semver-checks against 1.0.0: additions only.

## Upgrading from 1.0

Nothing to change. Code that relied on `io::DecodeReader` ignoring bytes after a raw or zlib stream should call `with_trailing_data(true)`. Compressed output at levels 4 to 9 differs from 1.0 (it is valid DEFLATE and smaller on every benchmark corpus), so tests that compare those bytes with stored ones need new fixtures.
