# compress-lib v0.8.0 - Alpha

**Used the way its consumers use it, and checked against C zlib on both sides.** v0.8.0 exercised the WebSocket, HTTP, and server paths end to end and added a CI check against C zlib itself.

## What's in 0.8.0

- WebSocket permessage-deflate, as ws-net calls it: every combination of server and client window bits (8 to 15) and context takeover, messages split into frames at random points, the per-message budget (`OutputLimit` maps to close code 1009, other decoding errors to 1007), and a message prepared once and broadcast to connections with and without takeover.
- HTTP content codings, as http-net calls them: a gzip body decoded as it arrives in chunks of 1 byte to 64 KiB with output and ratio caps, and a body with two codings (`Content-Encoding: deflate, gzip`) decoded by two chained streaming decoders.
- Streamed responses, as serve-net writes them: server-sent events sync-flushed one by one, each decodable as soon as it is on the wire; an encoder reset and reused for every response.
- A compile-time check that every engine is `Send` and `Sync`.
- Interoperation with C zlib in CI, through CPython's `zlib` and `gzip` modules: compress-lib decodes CPython's raw, zlib, gzip, and multi-member gzip streams at levels 0, 1, 6, and 9, and CPython decodes every stream compress-lib writes, sync points included.

The two issues ws-net found while integrating 0.6.0, quadratic CPU from byte-by-byte fragments and a cut-short final block accepted at a message end, were fixed in 0.7.0. Building permessage-deflate into ws-net itself (with the Autobahn compression sections) is ws-net's milestone, against this release's `message` API.
